# Nexora 生产就绪差距评估

**评估日期**: 2026-07-13
**评估目标**: 有真实用户、不可容忍停机/数据异常、无人值守、承载关键业务、高可用 + 强一致
**评估方法**: 逐项源码核查(标注 file:line),非报告转述

> 结论先行:**按上述目标,当前不可上生产。** 差距为架构级,非打磨级。
> 代码库自身在集群启动时打印 "EXPERIMENTAL — NO FAULT TOLERANCE ... Do NOT
> rely on this for high availability"([main.rs:1033](../../crates/nexora-app/src/main.rs))
> —— 作者立场与该目标直接冲突。达标需数周至数月专项工程,其中共识层为 4–8 周架构投入。

## 二、P0 阻断项(不解决绝不能上)

### P0-1 强一致读未闭环
- **现状**: `quorum_read.rs:161-176` 拿到多数派响应后 `drain().next()` 取任意一个,不比较版本/时间戳。并发写场景下可读到旧值。
- **补齐**: 为每个属性写引入单调版本(或 HLC 时间戳),quorum read 在响应集里选最高版本;读修复(read-repair)回写落后副本。
- **工作量**: 1–2 周(含版本存储改造 + 测试)。
- **前置**: 依赖 P0-4 的复制进度/版本基础设施。

### P0-2 写不丢需真实共识
- **现状**: 当前 primary-backup + quorum ack。owner 在写已 ack 但未充分复制时崩溃,failover 到落后副本会丢已确认写。
- **补齐**: 要么(a)引入 Raft/Paxos 让写走多数派日志提交,要么(b)严格 W+R>N + 同步复制 + fencing,并证明其在各故障组合下不丢。(a)更彻底但重。
- **工作量**: (a) 4–8 周架构级;(b) 2–3 周但保证较弱。
- **决策点**: 关键业务 + 强一致,倾向 (a)。

### P0-3 崩溃恢复正确性未验证
- **现状**: WAL + group commit 存在(`wal/log.rs`),但无"进程 kill → 重启 → replay → 数据一致"的端到端故障注入测试。
- **补齐**: 崩溃注入测试矩阵(写中途 kill、fsync 前后 kill、多节点同时 kill),验证 replay 后无丢无重。
- **工作量**: 1–2 周。

### P0-4 分布式共识架构缺失
- **现状**: `--raft-port` 明确是骨架,非共识(`main.rs:911-919`)。ShardMap 变更靠 `propose_shard_map_update` + quorum_healthy,非日志复制共识。
- **补齐**: 引入成熟 Raft 库(如 `tikv/raft-rs`)管理 ShardMap 元数据与/或数据日志;适配写路径、成员变更、failover。
- **工作量**: 4–8 周(架构级,影响面最大)。
- **风险**: 引入新故障模式,需大量新测试。

### P0-5 成熟度/信心
- **现状**: 真实多进程 e2e 本轮才首次运行,立即暴露 2 个基础 bug。无人值守要求系统在无人时自处理故障组合,而当前有人盯着仍在发现基础问题。
- **补齐**: 大幅扩展真实故障场景的 e2e 覆盖(见 P1 各项),积累"跑过很多遍都绿"的记录。
- **工作量**: 贯穿全程,随其他项累积。

## 三、P1 项(生产必须,但非绝对阻断)

- **P1-1 分区/脑裂验证**: 注入网络分区(iptables/tc),验证少数侧 fail-closed、多数侧继续、愈合后收敛。~1 周。
- **P1-2 集群负载/容量基线**: 多节点吞吐/延迟/尾延迟压测,给出容量规划数字。~1 周。
- **P1-3 长稳 soak**: 72h+ 持续负载 + 周期性故障注入,观察内存/句柄泄漏、性能衰减。~1 周 + 观察期。
- **P1-4 备份恢复**: 实现并演练一致性快照 + 时间点恢复。~1–2 周。
- **P1-5 failover 告警钩子**: failover/降级事件推送到 ops(webhook/PagerDuty)。~2–3 天。
- **P1-6 CI e2e 稳定性**: 已加 `cluster-e2e` job([ci.yml](../../.github/workflows/ci.yml)),需观察真实 runner 上是否 flaky,必要时调时序窗口。观察若干次。

## 四、P2 项(完备性)

- **P2-1 `remove_node` 缩容端到端**: 补多进程 e2e(对称于已有的 add_node)。~2–3 天。
- **P2-2 滚动升级**: 版本兼容协议 + graceful drain。~1–2 周。
- **P2-3 运维 runbook**: 故障处置手册、监控面板、告警阈值。~3–5 天。

## 五、建议的推进顺序

依赖关系决定顺序,不是简单按优先级并行:

```
阶段 A(强一致基石)      P0-4 共识层 → P0-2 写不丢 → P0-1 强一致读
阶段 B(可靠性验证)      P0-3 崩溃恢复 + P1-1 分区/脑裂(可与 A 后段并行)
阶段 C(生产运维)        P1-4 备份 + P1-5 告警 + P1-2/3 负载/soak
阶段 D(完备)            P2-1 缩容 + P2-2 滚动升级 + P2-3 runbook
```

**粗略总量**: 若走 Raft 路线(P0-4 取 a),整体 **约 3–5 个月**专项工程 + 一段真实灰度观察。若走强化 primary-backup(P0-2 取 b,一致性保证较弱),可压缩到 **约 2–3 个月**,但与"不容数据异常"的目标存在张力。

---

## 六、给决策者的话

1. **不要用当前状态承载你描述的关键业务。** 强一致读未实现、无真实共识、崩溃恢复未验证——这三条任一都足以在生产中造成数据异常。
2. **最务实的路径是分段逼近**:先在"可容忍停机、有人值守、数据另有备份"的非关键场景灰度,积累真实运行数据,同时按阶段 A→D 补齐;而非一步到位上关键业务。
3. **共识层(P0-4)是最大决策点**:它决定整体是 3–5 个月还是 2–3 个月,以及最终一致性保证的强度。上关键业务前必须先定这个方向。
4. 补齐过程中,**同步移除/更新代码里的 "EXPERIMENTAL" 横幅**,让系统的自我声明与实际能力一致——否则要么是横幅在说谎,要么是能力没到位。
