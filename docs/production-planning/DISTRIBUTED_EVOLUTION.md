# 分布式演进全景

**状态**: 提案 | **生成日期**: 2026-07-08 | **依据**: 对分布式/存储/计算路径的源码逐项审计

> 这是一份**全景**文档，把"完整分布式图数据库"拆成**四条正交的工作线**，说明每条线的现状、依赖、工作量，以及它们之间的关系。目的：避免"做了 HA 就以为分布式存储/计算也自动有了"这类误解。
>
> HA 那条线的详细阶段计划在 [HA_ROADMAP.md](HA_ROADMAP.md)，本文档引用它、不重复。

---

## 0. 核心认知：四条正交的线，不能互相推导

一个常见误解是"实现了分布式，存储/计算/HA 就都有了"。实际上这是**四个独立的维度**，实现其中一个不会附带另外三个：

| 工作线 | 回答的问题 | 与其他线的关系 |
|---|---|---|
| **分布式存储** | 数据放在哪些节点 | 是分布式计算和 HA 的**共同前置** |
| **分布式计算** | 查询在哪里执行（下推 vs 拉回） | 依赖分布式存储；与 HA 无关 |
| **高可用（HA）** | 能否扛节点故障 | 依赖分布式存储；与分布式计算无关 |
| **单机性能** | 单节点多快 | 独立，已完成 6 项优化 |

**关键结论**：做完这四条线，得到的是一个成熟的 **shared-nothing（无共享）图数据库**——数据分片 + 每片有副本 + 计算贴着数据跑。这**不是**存算分离架构（见 §5）。对 Nexora 的"实时流式"定位，shared-nothing 是正确选择；存算分离只适合冷数据/分析层（混合架构）。

### 一张现状总表

| 工作线 | 现状 | 差距量级 |
|---|---|---|
| 分布式存储 | ⚠️ 路由/ShardMap 有，但写路径不走 router（各节点只服务本地图） | 中（HA 阶段 1 会补上地基） |
| 分布式计算 | ⚠️ scatter-gather 原语已写，但 Cypher 执行器不用它（拉回本地单机执行） | 中（原语现成，缺接线） |
| 高可用 | ❌ pre-alpha 脚手架（无复制、无真 failover、无真 Raft） | 大（3-4 人月，见 HA_ROADMAP） |
| 单机性能 | ✅ 已优化（索引分片、WAL、快照并发化） | 完成 |
| 分层存储（混合） | ⚠️ 冷层零件就绪（S3 真实），但图数据不流经它 | 中大（核心缺口未做） |

## 1. 依赖关系图（为什么顺序重要）

```
                    单机性能 ✅（已完成，独立）

分布式存储地基
（写路径接 router）
= HA 阶段 1                    ← 一个地基，三条线共享
   │
   ├─────────────┬──────────────────┐
   ▼             ▼                  ▼
HA 阶段 2-5    分布式计算          分层存储
（复制/failover）（scatter-gather   （图数据下沉到
               接进执行器）        Warm/Cold 层）
   │             │                  │
后台 HA          实时遍历/          冷数据弹性+成本
                聚合下推            （混合存算分离）
```

**核心洞察**：「写路径接 router」这个地基（即 HA 路线图的阶段 1）是**三条线的共同前置**。一旦它完成：
- HA 可以往下做复制（阶段 2-5）；
- 分布式计算可以把 scatter-gather 接进执行器；
- 分层存储可以让冷数据下沉。

所以阶段 1 是**回报最高的单点投入**——它同时解锁三条线。反过来，跳过阶段 1 直接做任何一条都是空中楼阁（当前 HA 代码"切到空节点"就是这个错误）。

---

## 2. 工作线 A：分布式存储

**目标**：数据真正分片到多个节点，写读跨节点路由。

**现状**：`ShardMap` + 一致性哈希路由存在，但 `handlers.rs:552` 写直打本地图，`AppState` 无 router——各节点只服务本地图。

**要做**：即 [HA_ROADMAP](HA_ROADMAP.md) 的**阶段 1**（写路径接 router + 单主路由）。这条线的地基和 HA 的地基是同一个。

**额外（路线图未覆盖）**：分片再平衡、扩缩容时的数据迁移。这是 shared-nothing 的固有成本（加节点要搬数据），属于 v2 话题。

**工作量**：阶段 1 = L（1-2 周）；再平衡 = 另一个 L-XL。

---

## 3. 工作线 B：分布式计算

**目标**：查询/遍历在数据所在节点就地执行、合并结果（把计算推向数据），而不是把数据拉回协调者单机算。

**现状——最有意思的一条线**：
- 分布式计算原语**已经写好**：`scatter_gather_traverse`（`router.rs:158`）——把遍历下推到各 shard 并行执行、合并 frontier。
- 但它的生产调用者是**空的**（只在测试/local_client 里被调）。
- Cypher 执行器走**反模式**：`all_node_ids()` 把全部节点拉回协调者本地单机执行（`executor.rs:116`）——这正是单机性能评估里"全量快照拷贝、无 pushdown"问题的分布式版本。

**要做**：让 Cypher/SQL 执行器在跨 shard 查询时**调 scatter-gather 而不是拉回本地**。因为原语现成，主要工作是执行器的查询规划：识别哪些查询可下推（遍历、按 shard 可分的聚合）、如何合并部分结果。

**依赖**：工作线 A 的阶段 1（要先有跨节点数据平面才能下推）。

**与 HA 无关**：复制/failover 一点都不会带到这条线——这是纯粹的查询执行优化。

**工作量**：L-XL（原语现成降低了成本，但查询规划器改造不小）。

---

## 4. 工作线 C：高可用（HA）

**目标**：节点故障不丢数据、不停服务、防脑裂。

**现状**：pre-alpha 脚手架——无复制（RF=1）、failover 切到空节点、"Raft"无选举发空 payload。详见 [HA_ROADMAP §0](HA_ROADMAP.md)。

**要做**：HA_ROADMAP 的阶段 1-5（阶段 1 是共享地基；2 复制；3 state transfer；4 failover+fencing；5 混沌测试）。

**依赖**：阶段 1（共享地基）。**与分布式计算正交**——HA 是数据冗余/容错，不涉及计算在哪跑。

**工作量**：3-4 人月（详见 HA_ROADMAP §4）。

**现状已诚实化**：阶段 0（启动告警 + 文档标注实验性）已落地。

---

## 5. 工作线 D：分层存储（混合存算分离）

**目标**：热数据留在本地（shared-nothing，保实时），冷数据/历史下沉到共享对象存储（存算分离，拿弹性+成本）。这是一个**混合架构**，不是纯存算分离。

**现状——零件就绪，主发动机未接**：
- `TieredStore`（`nexora-storage`）接口层真实，main.rs 有 `--storage-backend=s3/local` 构造，lifecycle 规则（Hot→Warm 按 age 迁移）可用。
- **Warm 层是真的**：S3 backend 是真实 HTTP + SigV4（GAP-2 修复），兼容 S3/MinIO/R2。
- 有运维 API：`GET /storage/status`、`POST /storage/migrate`。

**两个决定性缺口**：
1. **Hot/Cold 层是 `MemoryStorage`（内存 mock）**（main.rs:610/616），不是 RocksDB。所谓"热层本地 RocksDB"没接——热层是内存。
2. **图数据完全不流经 TieredStore**。图引擎持久化走 `RocksDbPersistor`（本地），`TieredStore` 是一条**完全平行、不相交**的对象存储线——只有那两个手动 blob API 碰它。没有任何代码把 node/edge/fragment/snapshot 写进分层路径。

**激活清单（按依赖顺序）**：

| 层 | 现状 | 要激活需要 | 量级 |
|---|---|---|---|
| Hot | ❌ 内存 mock | 换成 RocksDB backend | 小（接线） |
| Warm (S3) | ✅ 真实 HTTP | 已就绪 | — |
| Cold | ❌ 内存 mock | 换成 S3/Iceberg backend | 小（接线） |
| **图数据 → 分层** | ❌ **不相交** | **把 fragment/snapshot 冷数据下沉接进 TieredStore** | **中大（核心）** |
| 冷数据读回 | ❌ 无 | 读路径按 fragment 时间范围命中冷层并拉回 | 中 |
| 冷层查询下推 | ❌ 无 | Parquet/Iceberg 列存下推 | 大（可选） |

**核心工作**是把 `nexora-fragment`（`fragment/lib.rs`：按时间窗分片的不可变 fragment，934 行）的生命周期和 `TieredStore` 的 lifecycle 打通——fragment 天然是分层落盘的单位。

**依赖**：工作线 A 的阶段 1（跨节点数据平面）。**规模与 HA 阶段 2-3 相当**，不是接线量级。

## 6. shared-nothing vs 存算分离（为什么四条线做完不等于存算分离）

**做完 A+B+C 得到的是 shared-nothing，不是存算分离——两者方向相反。**

| | Shared-Nothing（四条线的方向） | 存算分离（Disaggregated） |
|---|---|---|
| 数据在哪 | 钉在计算节点本地盘 | 共享存储层（S3/分布式FS） |
| 计算节点 | 有状态——拥有自己的数据 | 无状态——按需从共享层拉 |
| 扩容 | 加节点 = 搬数据（再平衡） | 计算/存储独立扩，不搬数据 |
| 容错 | 数据多副本 + failover（HA 阶段 2-4） | 存储层自己保证持久，计算节点随便换 |
| 代表 | Neo4j Cluster、TiKV、Cassandra | Snowflake、Neon、Aurora、RisingWave |

**存算分离优劣**：
- 优：弹性伸缩（算力秒级增减不搬数据）、成本（算力可缩到零、冷数据落廉价对象存储、只存一份）、运维简单（无状态计算节点挂了直接换）、读扩展易。
- 劣：**延迟**（读走网络到共享层，对低延迟 OLTP/实时遍历是硬伤）、**写路径复杂**（对象存储最终一致、不适合高频小写）、**对图遍历尤其不友好**（每一跳都可能是网络往返）、共享存储成带宽/IOPS 瓶颈。

**对 Nexora 的判断**：其定位是**实时流式 + 低延迟遍历**，存算分离的网络读延迟正好打在软肋上；图遍历的随机小读，shared-nothing 的"计算贴数据"（scatter-gather 的哲学）天然更优。所以**热路径必须保持 shared-nothing**。存算分离的价值场景是 OLAP/分析/弹性——正好对应工作线 D 的**冷层**。

**结论：Nexora 的正解是混合架构——热路径 shared-nothing 保实时，冷数据/历史分析下沉到存算分离的共享层拿弹性+成本。** 别把整个系统改成纯存算分离，那会毁掉实时延迟。现有的 Tiered（Hot 本地 / Warm S3 / Cold Iceberg）设计意图正是这个混合方向——只是还没接通（工作线 D）。

## 7. 建议的推进顺序

1. **阶段 1（写路径接 router）—— 最高优先级**。它是三条线（A/B/C）的共享地基，一次投入解锁三条线。L 量级。
2. 之后按业务优先级选分支：
   - 要**容错** → HA 阶段 2-5（3-4 人月，数据正确性工程，需专门评审）。
   - 要**大图查询快** → 工作线 B（scatter-gather 接进执行器，原语现成）。
   - 要**冷数据弹性+降本** → 工作线 D（fragment 下沉，中大）。
3. 每条线都应作为**独立里程碑立项**，不宜夹在日常优化里——它们都涉及数据正确性或跨节点一致性。

**不要做的事**：跳过阶段 1 直接做任何分支；把热路径改成纯存算分离；把这四条线当成"做了一个就都有"。
